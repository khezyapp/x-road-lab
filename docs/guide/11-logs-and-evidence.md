# 11 — Logs and Evidence

**Goal:** turn an error into a request ID, a detail UUID, and a specific log line.
**Time:** 5 minutes.

## Find the IDs first

Every X-Road REST response can carry:

- `X-Road-Request-Id` — identify the request.
- `X-Road-Id` — identify the message.
- body `detail` — a UUID for the server-side error details.

Capture them before the terminal scrolls away:

```bash
curl -sS -D /tmp/error-headers.txt -o /tmp/error-body.json -X POST \
  "http://localhost:4310/r1/DEV/COM/1234/TestService/noSuchService" \
  -H "X-Road-Client: DEV/COM/4321/TestClient" \
  -H "Content-Type: application/json" \
  -d '{}'

cat /tmp/error-headers.txt
cat /tmp/error-body.json
```

`X-Road-Request-Id` and the body `detail` UUID are the keys to the logs.

## Container and component logs

```bash
cd /tmp/xroad-7.8.3/Docker/xrd-dev-stack

docker compose -f compose.yaml -f compose.dev.yaml --env-file .env ps --all
docker compose -f compose.yaml -f compose.dev.yaml --env-file .env logs --tail=100 ss0
docker compose -f compose.yaml -f compose.dev.yaml --env-file .env logs --tail=100 ss1
docker compose -f compose.yaml -f compose.dev.yaml --env-file .env logs --tail=100 cs
```

`docker compose logs` shows the service's stdout/stderr. X-Road application logs are files inside the container:

```bash
docker exec ss0 sh -c 'ls -l /var/log/xroad'
docker exec ss0 sh -c 'tail -n 100 /var/log/xroad/proxy.log'
docker exec ss0 sh -c 'tail -n 100 /var/log/xroad/configuration_client.log'
docker exec ss0 sh -c 'tail -n 100 /var/log/xroad/signer.log'
```

On SS1, use `ss1` instead of `ss0`.

Search for the detail UUID or request ID:

```bash
docker exec ss0 sh -c 'grep -R "PASTE-UUID-HERE" /var/log/xroad 2>/dev/null | head -20'
docker exec ss1 sh -c 'grep -R "PASTE-UUID-HERE" /var/log/xroad 2>/dev/null | head -20'
```

## Which log answers which question

| Log | Answers |
| --- | --- |
| `proxy.log` | Routing, ACL, provider connection, service errors. |
| `clientproxy_access.log` / `serverproxy_access.log` | Per-request access trail. |
| `configuration_client.log` | Global configuration download, signature verification, anchor problems. |
| `signer.log` | Keys, certificates, OCSP, signing. |
| `docker compose logs <service>` | Startup failures, crashes, port/DB problems. |

## UI diagnostics

Both Security Servers have a **Diagnostics** page. Use it to check:

- global configuration version and freshness,
- timestamping service connectivity,
- connection tests to the Central Server and peer Security Servers.

Diagnostics is often faster than reading logs for "the SS cannot reach the CS/TSA/peer" problems.

## What to capture for a bug report

```text
Request:
  method:
  URL:
  X-Road-Client:
  body/content-type:

Response:
  status:
  X-Road-Error:
  X-Road-Id:
  X-Road-Request-Id:
  body (including detail UUID):

State:
  consumer SS client state:
  provider service description enabled:
  ACL subject present:
  global configuration fresh:
  clock synchronized:

Logs:
  proxy.log / configuration_client.log / signer.log excerpts
```

This is enough for another engineer (or a future agent) to reproduce the failure without guessing.

## If a log file is missing

| Symptom | Meaning | Fix |
| --- | --- | --- |
| `/var/log/xroad` empty | Wrong container, or the service has not started. | Check `docker compose ps`; use `ss0`/`ss1`, not the host. |
| `permission denied` | You are not the right user in the container. | Use `docker exec -u root` only for inspection, or read with the container's default user. |
| Log is stale | The request went to the other Security Server. | Consumer calls hit SS1; provider errors are on SS0. Check both. |
| UUID not found | The error was generated by the other SS, or logs rotated. | Search both containers; check the access logs. |

## Why this step exists

The response body tells you **what** failed. The request ID and detail UUID tell you **where** to look. Without them, you end up restarting containers and changing configuration at random.
